## Outcome and boundaries

A user viewing Step 6 can answer: why this score, what lowers it most, which effective rules were applied, and whether REJECT means a low aggregate or a blocking rule forcing zero. Both Step 5 and Step 6 must use the available centre width without horizontal scrolling or clipped information. Details expand beneath a contract, never into extra columns or a lateral drawer.

Preserve scorer behaviour, contract recommendation policy, prices, stars, charts, picks, sorting, filter/limit handling, card rescue, Step 7 recompute/order flows, and historical watch grading. This is explanatory work, not a scoring-policy change. Do not reconstruct the screenshot's score 68 from invented component values.

## Proposed overview

Within each symbol group use a compact summary grid: star / contract identity with score+badge adjacent / DTE / delta / price / spread / explain button / pick control. Long labels wrap. The score's sort control lives in the identity/score header. Preserve every existing sortable metric through a labelled sort selector (contract, DTE, delta, price, IV, IV percentile, theta, spread, volume, score; both directions) when its column moves into detail. Optional wider-width metric columns are permitted only if measured centre width supports them.

Group header shows stock symbol, returned count and available status counts derived only from fetched rows, chart control, and collapse state. Never call an empty result 'all rejected' or 'no eligible contracts': filters/limit/fetch availability are not rejection statistics. Keep no candidates, initial loading, empty returned chain, refresh, failure, rescued-row warning and unavailable data distinct. Preserve current one-open-symbol behaviour; performance validation can inject/open all groups as a deliberate stress harness, not silently change accordion policy.

Above the list, show a compact Rules applied panel with weights and exact aggregate boundaries from returned evaluation snapshots. Only use a global label when snapshots agree; otherwise say rules vary and expose per-contract rules. No header fallback to YAML hardcoded values or current live Step-3 edits. Show default grading warning for scans without recorded contract_rules as currently required.

A keyboard-operable Explain button with `aria-expanded` and `aria-controls` opens a region immediately below the row; opening does not select/star the contract or fetch data. Initially all explanations are closed. Five component cards/table rows wrap into the available centre space. Each shows raw sub-score /100, actual weight, contribution in score points, observed inputs and preferred/hard thresholds with units and comparison operators. OI is part of liquidity, not a sixth weighted component. IV percentile, theta and premium price are clearly contextual; neither is presented as directly weighted. Price influences spread percentage through bid/ask mid, not a sixth price score.

Below components show largest weighted losses (weight*100 minus contribution), ties handled stably; this means largest lost points, not lowest raw sub-score. Separately list every blocking reason and active observed/threshold comparison. Blocked score shows 'Score forced to 0 by blocking rule(s)' and any component contributions are explicitly diagnostic, not the cause of displayed zero. Unblocked low aggregate shows rounded aggregate below caution boundary. Missing explanation is 'Explanation unavailable for this result'; an absent reason list is not evidence checks passed.

Spread type/net debit-credit/max gain/max loss/breakeven move to a wrapping group-level section, identified as the scan candidate's spread snapshot. Current row code repeats candidate-wide spread values for different single-leg rows: never relabel them as newly priced values for each alternate contract. Do not invent whole-spread scoring; explain the actual returned single-contract grade and preserve the spread badge/context.

1. Add a versioned, optional `explanation` field on OptionContract with a typed server-owned evaluation model. Suggested content: scorer contract identity, version, evaluated-at/date, `outcome` (blocked / aggregate), actual weights keyed to the five wire components, status thresholds, observed quantities with units/basis, preferred and hard effective bounds, existing reject reason codes and soft flags, named structured blocker comparisons, soft fail count/limit, unrounded aggregate and rounded aggregate only where aggregate scoring actually ran. Include per-component server-calculated contribution and lost points, and only meaningful known values; missing raw inputs stay distinguishable from scorer-normalized zero. Unknown future reason codes must remain visible, not silently map to a pass.
2. Build this from the SAME final immutable `cfg` and calculations used in `validate_contract`, on BOTH return paths. Do not evaluate rules a second time in the router/browser. Derive structured blocker observations at the existing guard sites (or share their evaluation result); preserve all existing labels/order and guards, including volume zero plus adequate OI exemption, IV basis-dependent ceilings, stock score and `soft_fail_count >= max_soft_fail_count`. Missing IV contributes neutral 50 and `no_iv_rank_data` counts as a soft flag today.
3. On unblocked results expose weighted aggregate in the exact existing five-term order, server `round` result and configured status thresholds; do not normalise weights, truncate fractional thresholds, or replace Python ties-to-even with JS Math.round. Existing score/status must remain byte-for-byte equal for the same inputs. On blocked results do not fabricate a rounded aggregate that the scorer never computed; diagnostic contributions can be supplied clearly separately, but score is 0 and all blockers are authoritative.
4. Route maps scorer explanation directly, alongside current optional breakdown. Keep GET list shape, query parsing, max price/limit, full-chain IV augmentation, stable ties and rescue exemptions unchanged. New models must accept real fractional thresholds; broad `_safe_detail` swallowing must not silently discard valid explanation. Do not echo arbitrary raw config/secrets; explicit finite typed fields only.
5. No DB migrations, grading schema changes or scan-wide snapshot changes are necessary for this Step-6-focused API contract. Existing scan card consumers remain compatible because explanation is optional. If a later stage needs scan-card explanations, scope and independently audit their producer path separately; never pretend the older scan payload contains new data.
