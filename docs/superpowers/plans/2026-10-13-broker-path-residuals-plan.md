## Decisions and invariants

Kenneth's answers in this chat on 2026-10-13:

1. An uncertain submission stays blocked until manual verification at the broker. A durable attempt ID survives retry/restart and prevents duplicate submission.
2. An increase in Portfolio quantity represents an added fill; its price is required and average entry is weighted by quantities.
3. If that already-completed fill breaches exposure caps, record its full quantity and warn. Never clamp or reject the actual fill to fit the cap.

Keep the existing hard-delete approval cleanup policy; fix the orphan race, not approval retention policy. Preserve bearish OPEN refusals, CLOSE availability, the IBKR confirmation refusal, Tradier admission refusal, durable daily-risk reservations, authoritative server account value, numeric bounds and late-422 companion-field persistence. Submitted/accepted is not filled. Never infer rejection from HTTP status alone or from a generic exception class once adapter submission starts.

## Proposed contracts (review before build)

### Durable submission identity

Accept optional `attempt_id` on both manual order requests, including CLOSE; mint a durable server UUID for legacy callers that omit it. Before minting/dispatch, a durable canonical fingerprint lookup must replay/block an existing unresolved attempt with the same payload. Uncertainty fingerprints do not expire across restarts; legacy callers cannot bypass a hold by obtaining a new UUID. Explicit IDs remain payload-bound. Keep successful fingerprints durable too: an automatic ID-less retry must replay its existing known outcome even after a lost HTTP reply/restart. A short cache may accelerate reads but time alone never authorizes another POST; unresolved fingerprints never expire. An explicit new ID cannot bypass unresolved fingerprint protection. Canonical payload binds endpoint kind, broker, symbol, exact normalized instrument, action, effect, quantity, order type, limit, tif and conid. No rounding or coercion may make distinct executable payloads match. An ID reused with another payload returns 409 and never dispatches. A deliberate new intent with an explicit ID is separate only after the previous unresolved intent is verified; time passing never clears uncertainty. Legacy callers require a fresh explicit attempt ID or a uniquely new server-prepared row to prove distinct deliberate intent; their identical automatic retries replay known outcomes indefinitely. CLOSE and standalone legacy requests without fresh prepared-row proof also replay the prior identity; deliberate repetition uses a new explicit ID.


**Production identity resolution (lost-success response):** before manual routes claim dispatch, resolve the durable identity rather than calling the low-level ID-less compatibility claim directly. An explicit supplied ID remains payload-bound. For ID-less requests, use a stable server identity tied to the exact prepared-row intent when one exists (derive from its immutable recId/scope or retain a durable mapping); both first requests and retries use the SAME identity. Ownership must be validated under the database guard, never from an unlocked/stale selector. A genuinely new unowned prepared row may identify a new intent only after prior uncertainty is resolved; an already-owned row identifies its existing attempt, not a new one. When no new prepared-row proof exists, look up/replay the retained canonical-fingerprint attempt even if submitted/filled or its saved row was deleted; otherwise create one stable standalone legacy identity. New explicit IDs still cannot bypass an unresolved matching fingerprint. The T1 generic short-success compatibility method is not production dispatch authority: T2 must always pass this resolved durable ID. Tests must simulate server-known success plus lost browser reply, four-second delay, new process/service and retry with no client ID: one total broker POST for OPEN and CLOSE. A new explicit ID or freshly prepared new row proves intentional later submission; a timer never does.
Persist attempt before any possible submission. States distinguish preparing, dispatching, proven-not-submitted, submitted, filled and outcome-unknown. Store authoritative broker order ID/status separately from app outcome; store original response/refusal for repeat reads. Explicit existing IDs are read-only on repeat submission, including a proven refusal. A legacy retry after proven refusal may create a new ID because no prior order was submitted; unknown never may. Missing/corrupt attempt storage or inability to commit the dispatch claim fails closed before adapter entry. No in-memory event/cache is an authority.

Use an atomic database compare/update or unique insertion for leadership. Serialize fingerprint lookup plus insertion under the exposure guard, so concurrent ID-less callers cannot mint competing attempts; use a unique active-fingerprint constraint or equivalent guarded invariant. Test two different explicit IDs with the same unresolved fingerprint as well as ID-less callers. Mark dispatching durably BEFORE adapter entry. Same-ID waiters read the leader result or pending/unknown result; they must never become a replacement dispatcher after error, cancellation or restart. A restart treats dispatching/preparing attempts conservatively as requiring reconciliation (no lease expiry redispatch). Cancellation after worker start retains durable unknown and risk; worker completion may record a known authoritative outcome, but no second dispatch or automatic booking is launched by cancellation recovery. If outcome persistence fails after broker entry, the persisted claim still blocks replay and retains holds.

Adapters supply typed proof for pre-submission refusal and broker-response rejection only where the actual response shape proves rejection. Unexpected JSON shape, invalid JSON, missing/placeholder order ID, unknown status, SDK result dereference failures, transport exceptions and unproven HTTP errors after POST are unknown. IBKR's exact confirmation shape remains proven not placed because this app never confirms it. `OrderAdmissionRefusedError` remains before-POST semantics. Accepted/PreSubmitted/Submitted/pending results with a usable ID are submitted; `filled` requires authoritative fill status. Partial fills are not fully filled.

Expose GET attempt and manual verification mutation with an explicit verification outcome and broker evidence note. Mutation never calls an adapter or creates a new ID, and is compare-and-set against unresolved state so a late worker and verification cannot silently overwrite each other. Require verification, not a generic dismiss/reset. Keep daily spend for verified submitted/filled/partial or canceled-after-submission outcomes. Only verified definitely-not-submitted can call existing daily `resolve(... definitely_not_submitted=True)`. Verified canceled/partially filled orders retain conservative exposure coverage in this phase; precise release of partial quantities is deferred, visibly, rather than guessed. Unknown never releases any hold. Manual verification is an assertion by the user; no broker lookup/automatic retry is proposed.

### Exposure serialization and dispatch reservations

Use one database-backed exposure guard for all capacity-changing decisions, not only an asyncio create lock. A singleton row with insert-on-conflict + no-op UPDATE serializes Postgres transactions and SQLite writers, following the established daily-risk locking pattern. Obtain it BEFORE reading risk-relevant rows; ensure ORM objects are refreshed/expired so earlier SELECTs cannot reuse stale identity-map values. No network call runs inside its transaction.

For fire, a fresh, post-sizing exposure admission on the originating loop reserves the proposed exposure under that guard immediately before dispatch, using a synchronous worker bridge analogous to `DailyRiskHooks`. Commit the hold before POST. Pending/unknown/submitted-but-unbooked holds are counted by every create/PATCH/fire admission, survive restart and remain independent of deletable history. Fire booking transfers a hold to its exact row atomically; do not double count reservation and booked row. A failed/canceled booking retains the hold. Proven rejection removes exposure hold; unknown keeps it. Daily budget remains a separate conservative spend ledger with its existing UTC-day semantics.

For save-first manual sends, a saved row offsets a hold only through exclusive, durable ownership of its prepared-order coverage. Extend the Portfolio model with nullable server-written `prepared_order` metadata and `order_attempt_id`; migration leaves both null on existing inventory. `create_position` writes prepared metadata only on the gates-on save-before-order path when `body.orderType` is supplied: canonical instrument, symbol/action/effect (OPEN), final saved quantity, order type and exact limit. Gates-off auto booking and ordinary tracked basket rows never get that marker. Existing Options sends already pass these create-only fields; T3 updates stockDirectSend's `persistPosition` call to pass its existing order type/limit. No Options owner or api.ts edit is needed.

Under the shared database guard, a manual attempt may exclusively acquire an unowned prepared row only when this prepared scope exactly matches, quantities have not changed, and the row is still open. Optional savedRecId is a selector, never ownership proof. Legacy callers without it may locate a unique matching PREPARED row; matching an ordinary inventory row is forbidden. Transition that row's ownership durably to this one attempt before dispatch. A second distinct executable attempt cannot reuse its coverage, even after success-window expiry or manual verification. A proven-not-submitted attempt may relinquish unused prepared ownership for a later explicit attempt; an accepted/submitted attempt may not. Preserve the prior owner's audit linkage when relinquishing ownership. Multiple ordinary inventory rows or ambiguous prepared candidates get standalone additive holds; no fuzzy fractional strike match. Existing inventory plus a new identical one-contract OPEN therefore counts two contracts, not one.

Offset only this attempt's originally allocated portion, once: base inventory exposure plus distinct holds minus individually owned coverage, capped by both the hold and the currently retained allocated inventory. Added fill quantity is new inventory, never additional coverage credit for an older pending order. Sum distinct order attempts additively. Use conservative monetary basis so a higher order limit cannot be offset by a lower saved-entry amount. A deleted/mismatched prepared row cannot authorize a linked send. Deleting, closing or shrinking a linked row retains all uncovered pending/unknown exposure in the hold. Fire booking transfers ownership only to the row it creates for its own attempt; a reused or already-owned row cannot absorb another order. CLOSE identity does not release OPEN exposure merely because a close request is accepted; pending/unknown CLOSE never invents a local fill.

Do not change the existing cap math or treat daily risk reservation as a substitute for portfolio exposure admission. Never resize an already-dispatched order or an actual added fill to a smaller persisted quantity. Lock ordering is exposure guard then daily budget when both are required; no request session may hold a transaction while worker hooks wait for another session. Use separate short sessions for bridges and return immutable results to workers.

### Added-fill editing

Extend update request with `addedFillPrice` (finite positive) and expected previous quantity (`expectedQty`) to avoid applying a fill delta against a concurrently changed base. On increase, delta = requested total minus locked current quantity; new entry = `(old_qty * old_entry + delta * fill_price) / requested_total`. Preserve stored precision; round only where existing display contracts round. Evaluate full resulting exposure at that weighted entry. Stocks use multiplier 1; options 100. Reductions keep entry unchanged; this task does not invent close execution or realized P&L for existing quantity decreases.

A reported actual fill is indivisible: persist full resulting quantity and weighted entry even if the informational risk check refuses or suggests resize; return explicit exposure-breach warnings. This is Kenneth's confirmed decision. Subsequent pre-trade creation/fire admission must observe the full stored exposure and refuse new risk if necessary. Invalid/missing fill price or stale expected quantity still refuses the quantity/entry pair, preserving valid companion fields under the existing late-422 rule. Keep rung totals bounded by actually persisted quantity. Retain stored premiumStopPct unchanged: average-entry changes naturally move its dollar threshold under the existing fraction contract; no automatic dollar-preserving reanchor is authorized. Same-total retries do not apply another fill; stale expected quantity is a refusal, not another average calculation.

### Stops

Reproduce direction edge cases against the actual underlying/live quote, including equality, both directions, auto-plan re-anchor, user-set stop, structural stop, no live quote, zero/unset and an already-filled order. A bullish stop above entry is not evidence of a wrong-side stop: profitable trailing stops are reachable. Preserve existing specified user-stop live-price refusal and gates-off book-and-page behavior. Do not impose entry-side validation or change PATCH/structural/generated-stop policy without a decision. A reproducer that finds no violation becomes a characterization; it must not be represented as a red implementation test.

## Unresolved design questions and scope risks (explicit)

1. **Verification semantics:** user authorized manual verification and full-fill warnings. Proposed verification records submitted versus definitely-not-submitted with evidence; canceled-after-submission and partial orders keep conservative exposure holds. Precise quantity release, broker lookup and automatic fill reconciliation are deferred. Do not invent quantity/price or release daily spend. Auditor must check whether these conservative holds can meet acceptance without further product choices; if not, coordinator raises the exact choice before dependent build.
2. **Legacy saved-row linkage:** offset requires the server-written prepared metadata and exclusive durable ownership described above. Migrated marker-free inventory always yields an additive standalone hold. Old clients using the existing save-with-order-fields contract can claim only their unique new prepared row. Stock direct sends will supply those existing fields in their owned helper. Canonical fractional instrument parsing is required; never use integer strike truncation or infer coverage from symbol/quantity alone. No shared api.ts or Options owner edits.
