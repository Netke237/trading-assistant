# Candidate backtest artifact storage reconciliation

Phase `CANDIDATE-BACKTEST-CHART`, implementation source reconciliation after #235.

The existing durable report path uses SQLAlchemy async sessions against the configured SQLite/PostgreSQL database. `ScanReportBase` is an additive metadata registry, created at development startup and included by Alembic. Use that same registry for a new immutable `backtest_artifacts` table, with an additive Alembic migration after the current migration head. Import the model in startup/migration discovery. Do not store curve payloads in browser stores or change report retention.

Store schema version, opaque UUID, original/fresh provenance, scan identity, candidate identity, created/expiry timestamps and strictly finite serialized detailed evidence. Fetch by exact ID plus symbol; expired, unknown and malformed artifacts cannot fall back to another artifact. Use a bounded explicit retention window (30 days), checked on reads; cleanup may remove expired payloads while retaining small expiry metadata so an expired ID remains distinguishable. Original artifacts freeze bars, actual engine equity/fills and effective engine parameters/cash/cost configuration. A cached detail may be reused only when every input bar and effective engine input match; each scan linkage still carries its own scan identity. Aggregate-only legacy cache entries have no original chart evidence.

`_process_stock` already receives the scan ID. The report lifecycle wraps the scan callback with a collector; add report run identity there if needed, without changing report selection or generation behavior. Its allow-listed result projection currently omits unknown string fields; explicitly permit the new UUID field so report restoration preserves identity. Large details stay solely on the server. Original artifact capture/save is optional evidence: failure must preserve the original aggregate, ranking, gate and trading inputs.

The application's existing routers share a configured deployment boundary and have no per-user authentication dependency. Apply the same boundary to the artifact API; never introduce a separate public hosting path. Validate ID and symbol matching and never accept client-supplied artifact contents as original evidence.

Planned source families for BT-02: `backend/app/models/backtest_artifact.py`, `backend/app/services/backtest_artifacts.py`, `backend/app/routers/backtest_artifacts.py`, dedicated schema if necessary, additive migration, migration discovery/startup/router registration, `backend/app/routers/stock_scan.py`, `backend/app/schemas/stock_scan.py`, report lifecycle UUID projection and focused artifact/scan-linkage tests. Exact implementation details and tests remain the fresh ticket implementer's responsibility.
