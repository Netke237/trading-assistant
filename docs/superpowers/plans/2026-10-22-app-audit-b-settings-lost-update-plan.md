## Problem and acceptance

Two current same-origin tabs load Markov lookback35. A stores55. Stale B edits confidence caution64; today's whole-store persistence silently writes lookback35 again. Different-field and same-field stale edits must preserve the newer saved record or report an explicit conflict, with an explicit recovery path and verified reload/readback.

Choose conflict reporting, not automatic merging of financial settings. Preserve `bamendjou-settings`, version24, its serialized `{state, version}` shape, partialized fields, migrations, numeric values, validators, broker payloads and other stores' keys/versions. No backend, calibration, deployment, live provider, broker or notification work.

A synchronous read/check/write is insufficient: two tabs can both check the old bytes before either writes. Serialize cooperating Settings writes across tabs, then compare the exact last-confirmed bytes inside that critical section. A stale tab must not write. This requires asynchronous persistence receipts; memory updates remain synchronous, while callers needing durable completion await their receipt. That integration with broker/profile saves and the shipped ledger expands the initial L estimate to XL (>16h), complexity5. Split into three substantial M build units after clean plan approval.

## A. Browser critical section and Settings persistence

New `frontend/lib/settingsWriteLock.ts`: a small IndexedDB executor, usable on ordinary HTTP origins as well as HTTPS. Database `bamendjou:settings-write-lock`, version1, object store `mutex`; this is coordination only, with no settings values/credentials/financial data stored there. Open lazily on the first write. Every writer uses a **readwrite transaction on that same object store** and issues a request. Its success callback synchronously runs the entire localStorage read/check/write; no awaited work inside that callback. Resolve only on transaction complete. Capture and return the original callback error on abort. Open/upgrade/blocked/error/abort failures reject and perform no unprotected fallback write. Do not use a localStorage lease, a fake synchronous lock or secure-context-only Web Locks.

New `frontend/lib/settingsPersistence.ts`: factory for an independent tab/controller, plus the default browser instance. It exposes a `StateStorage` adapter and mutation-receipt capture. No import of settingsStore (avoid cycles).

- `getItem` remains synchronous, including hydration. Its first successful read of the Settings key records the exact baseline bytes, including null. Subsequent reads cannot silently clear an existing conflict or advance the confirmed baseline. Keep skipHydration and SSR behavior. A write queued before any confirmed read must not later become authorized merely because hydration finishes; reject it as unconfirmed initialization rather than overwrite an existing record. New-tab tests establish hydration before edits.
- `setItem` immediately registers a pending local write, including while database opening or another tab's transaction is pending. Serialize same-tab attempts FIFO as well as cross-tab critical sections. Under the lock, re-read the current bytes. A sticky conflict, missing confirmed baseline, or mismatch with this tab's last confirmed bytes rejects **before setItem**, retaining the newer stored record. On match, write the exact serialized value and advance the tab baseline only after the synchronous write succeeds. Keep that baseline if the transaction later reports failure: the write may already have reached localStorage, so receipt stays failed/unconfirmed until explicit recovery; do not replay an older baseline.
- Do not capture a stale baseline separately for each same-tab queued write: later writes use the controller's last confirmed baseline after the preceding operation settles. Thus two ordinary edits in one tab persist in order; a quota failure followed by a later successful local edit can recover without falsely diagnosing another tab.
- Preserve the actual thrown/rejected error object. Storage failures now arrive through the Settings action's Promise; this timing change is deliberate and must be threaded through relevant callers. Other three reporting stores remain synchronous.
- `removeItem` used through this adapter also goes through the critical section and baseline check. Do not introduce a direct-write/clear bypass. External storage changes/clear are conflicts, not automatic rehydration or write retries.
- Listen to native storage events for this exact key (or clear) on the same storage area. A different external snapshot marks a persistent conflict even if the event arrives after this tab's own write; do not ignore it merely because a later read equals this tab's most recent bytes. Never accept a storage event as proof that this tab's edited values were committed. Retain conflict until full page reload creates a fresh controller and hydrates the current bytes.
- Every cooperating write, including migration writes and explicit retries, must use this adapter. Ordinary tabs running this release are covered by the critical section; unchanged serialized data remains readable/migratable. Direct devtools/extension writes or a still-running older application cannot be forced to honor the new lock; any observed external change is treated as conflict. No claim of atomic cooperation with an older executable is made.

Mutation receipt capture must be explicit, without relying on Zustand's typed-void `set` return. A capture stack records the storage Promises synchronously produced by a mutation; nested captures include their own writes and the outer capture includes nested writes. `captureSettingsWrites(() => set(...))` returns a Promise for those writes. Synchronous validation remains before mutation. Attach rejection handlers internally so ignored event-handler return values do not create unhandled rejections, while an awaiting caller still receives the identical failure. Direct persist/setState writes still register in the ledger even without an action capture.

## B. Local pending/failure ledger and safe retry

Extend the existing **nonpersisted** `settingsSaveStatus.ts`; preserve remote attempt/discard/unconfirmed mechanisms exactly.

- Add a separate all-pending local registry. `trackLocalWrite(run)` registers synchronously, returns the original result/rejection, cleans its own settlement entry and does not create a remote `failed` receipt. `settleAll` loops over remote and local settlement promises, including newly started writes; global `isSaving()` includes both. Per-remote-channel queries retain their meaning.
- A local failure can carry a retry callback returning void or Promise and a fixed category (`storage`, `conflict`, or initialization/unavailable). Store serialized bytes only in memory, never render them or raw errors. For the guarded key, retry invokes the guarded adapter, under the lock, against the original confirmed baseline. **Never** directly replay guarded Settings bytes via global localStorage.
- A conflict has a fixed actionable message, is not automatically retryable and survives draft updates, successful unrelated writes, backend success, section navigation and repeated footer clicks. Example: "Settings changed in another tab. These edits are not confirmed. Reload the latest settings before saving again."
- `retryLocalWrites()` returns a Promise awaited by the footer. Preserve immediate synchronous behavior for default callbacks on the other three stores; await asynchronous guarded retries. Do not clear a replacement/newer failure when an older retry settles. No backend retry or unsent draft submission.
- A quota/security failure can be retried after storage recovers **only through the same guarded writer**. If another tab has written meanwhile, it becomes conflict and must not overwrite that newer record. A broker's backend failed receipt remains until its own later successful Save, even when a browser retry succeeds.

In Settings `page.tsx`:

- Show a persistent accessible Settings conflict notice immediately (not only after footer click), suppress Saved and explain that the current edits are not confirmed. Offer "Reload latest settings" with text explaining unsaved edits will be discarded. Use a full page reload, not partial rehydration that could leave stale section drafts. Disable reload while any tracked save is pending. No modal/automatic reload or backend submission.

- Risk's Settings writes remain after its confirmed backend response and outside the remote tracked callback, but await their receipts inside the existing try/catch. Local failure remains distinct from the already-confirmed backend receipt.
- Grep every runtime Settings setter caller with try/catch or an immediately following dependent action. Thread its Promise where completion/error semantics matter; do not turn unrelated pure numeric helpers into async APIs.

`searchProfileSnapshot.ts`'s `applySearchProfile` remains a regular function: keep synchronous strategy validation before any mutation; perform current in-memory mutations in their existing order; return a Promise for Settings receipts. Do not change scan requests/profile values or frozen-result invalidation. `SearchProfileBar` awaits it before marking a profile selected/applied, catches persistence failures and prevents a second overlapping apply (disabled pending dropdown plus synchronous guard/ref). Preserve validation-error behavior and avoid a late completion labelling another profile as applied. Other stores' write failures retain their existing semantics.
