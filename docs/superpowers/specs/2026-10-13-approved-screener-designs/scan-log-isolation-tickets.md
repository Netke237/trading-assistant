# Scan log isolation and persistence — required ticket amendment

12 October 2026. User requirement: a Stocks or Pre-Breakout run must not overwrite Options or any different scan category's log. Each category's latest run remains inspectable by the user and system until another run in that same category. This is a functional data requirement, not implemented by the presentation mockups.

This amendment supplements options-presentation-tickets.md and prebreakout-presentation-tickets.md; their frozen audit hashes remain unchanged. It supersedes any reading of PB-PRES-06 that would erase saved reports when parameters change. Existing presentation drafts remain plan-audited only; this amendment has its own audit record.

## LOG-01 — Durable, isolated latest-run records

- Maintain independent category keys for Options, Stocks, Pre-Breakout, Pullback and Fib Pullback. Pullback's use of postStockScan must not write the main Stocks category. Capture category at dispatch; changing the visible mode during a request must not change where its completion is written. Manual/scheduled/automatic runs must use the same explicit category mapping and identify their trigger.
- Within the application's existing user/account scope, save run identity, category, trigger, start/end timestamps, lifecycle state, resolved universe/symbol set, direction, horizon where applicable, effective parameter/config snapshot, stage counts, accepted/rejected/excluded symbols and observed reasons/values, data errors and warnings. Preserve the source-specific schema and meaning; do not coerce StockPipeline into OptionsPipeline. Record unavailable diagnostics explicitly.
- Persist the immutable report in durable backend storage and expose read-only lookup of the latest run per category and its run ID to the UI and system diagnostics. Browser storage alone is insufficient for system inspection. Reuse existing scan-session infrastructure when appropriate only after tracing its actual category/retention semantics; otherwise add an additive audited model/API. A normal scan result's absence of diagnostics is not a zero-failure report.
- No category-wide or global clear during another category's run. Page navigation, mode/parameter/universe changes, sorting, filtering, refresh, browser reload and ordinary app/backend restart must not erase saved reports. No TTL/background cleanup of the current latest report. No unbounded historical archive is required; retaining the latest report plus necessary in-flight/previous run is sufficient. Protect category-scoped retention from deleting a report referenced by another category.
- Keep effective scan parameters frozen on the report. Edited controls can show newer values, but the inspector must show the saved run's settings and a clear mismatch notice, not relabel old diagnostics as a new configuration.
- Migration: preserve existing storage keys and legacy Options/Stocks results and evidence. Do not infer category for an ambiguous legacy record; leave it explicitly legacy/unclassified and inspectable. Any changed persisted shape requires versioned migration and database upgrade as appropriate. New client storage keys use bamendjou:<name>.

## LOG-02 — Run lifecycle, failures and concurrency

- Opening/reading a report never initiates a scan. Starting another run creates a new identity/generation only for its own category. Keep the previous saved report readable while the new run is running; clearly distinguish previous completed report from current attempt/progress.
- A completed zero-candidate run is a valid new report. A failed run must retain its actual failure/stage diagnostics and terminal status, never display the old successful report as that failed run. When a failure/cancellation supplies no usable diagnostics, retain the previous report separately with its original timestamp and show the current attempt's explicit failure/cancellation and unavailable diagnostics. Do not delete the last inspectable evidence merely because a request failed before a report was produced.
- Category-local newest-started generation owns the latest-attempt pointer. A late completion from an older request must never replace a newer run's report. Use server-assigned ordering or equivalent transactional compare-and-set; client timestamps/completion order alone are insufficient. Overlapping categories update only their own keys. Candidate/report linkage uses run ID, never row index or global current-mode state.
- Persist accepted results and matching terminal report coherently, or expose explicit incomplete/report-unavailable state; never show counts from one run with symbols/parameters from another. Recover interrupted runs after restart honestly rather than leave a permanent running status.
- Persistence failures must be visible to the user/system. Keep the previous durable report and identify unsaved current diagnostics; no silent successful-save claim. Preserve existing frontend quota protection and backend error handling. Do not record credentials, tokens or secret exception payloads.

## LOG-03 — Inspector integration and verification

- Every category's Filter Breakdown/analysis log opens its saved report, with category, run ID, timestamps, status and frozen inputs. Provide system-readable retrieval using the same identity and data. Logs survive switching to another category and back, including browser reload. Missing legacy reports are unavailable, not empty successful scans.
- Keep report persistence independent of live table result-clearing behavior: changing parameters may clear candidates as today, but must leave the saved report accessible with its own survivors/rejections and snapshot labels. Do not rewrite the current trading inputs, candidate ranking or broker payload to restore a log.
- Required regression sequence: run Options A, Stocks B, Pre-Breakout C, Pullback D, Fib E; inspect all five after mode switches/reload/restart; run Options F and confirm B/C/D/E unchanged. Assert full contents and run IDs, not only counts.
- Cover same-category overlap with reversed completion order, switching modes mid-request, scheduled/manual overlap, failed/cancelled/no-data/zero-candidate runs, diagnostics absent, parameter edits, interrupted restart, storage write failure and legacy migration. Assert inspector and system API retrieve matching report contents.
- Cross-reference LOG-01/02 as prerequisites of PB-PRES-05/06 diagnostics and Options/Stocks inspector changes. Inspect all existing callers/setters/reset paths before implementation; a global rejectedLog or global latest-run pointer must not be reused for every category.
- Implement backend persistence/API and frontend integration as separate small stages. Verify Python 3.11 for backend tests; frontend typecheck and focused meaningful tests; fresh independent numeric/order/persistence audits, maximum three rounds per stage with shrinking follow-up scope. No app implementation or merge authorization is supplied by this draft.
